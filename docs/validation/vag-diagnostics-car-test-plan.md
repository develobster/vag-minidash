# Следующий тест Tiguan: CAN → ISO-TP → ECU

План от 2026-10-22. Это **план**, автомобильные результаты новой ветки отсутствуют.
[Исследование](../research/vag-diagnostics-deep-research.md) ·
[архитектура и ограничения](../architecture/vag-diagnostic-discovery.md).

## Подготовка

1. Сохранить известный рабочий canfix19 и проверить его manifest/hash по
   [исходному отчёту](../hardware/can-deep-analysis-2026-10-19.md).
   Для кандидата из feature-ветки нужны успешная ESP-IDF сборка, host-тесты и
   отдельная стендовая проверка. Этот PR сам не прошивает устройство.
2. Зафиксировать commit, версию app, профиль сборки, bench=OFF, CAN500,
   GPIO15/5, sample87.5%, `VAG_profile=none/UDS=off`, состояние экрана/тача.
   Не переиспользовать старый sdkconfig от другого профиля. Не менять загрузчик,
   разделы, калибровку, NVS и схему питания в рамках диагностического теста.
3. Выполнять на стоянке, с заторможенным автомобилем и свободным доступом к
   отключению устройства. Использовать существующую проверенную схему питания.
   Не соединять USB и OBD одновременно — это ограничение существующей аппаратной
   инструкции. Не менять терминаторы наугад и не измерять сопротивление живой шины.
4. Другой активный диагностический тестер на время опыта отключить. Reference
   ODIS/VCDS-проверку делать отдельным сеансом с разрешёнными read-only операциями.
   Никаких clear DTC, basic settings, output tests, coding/adaptation или flashing.
5. При необходимости сначала отдельный listen-only образ: 30 секунд при включённом
   зажигании, записать RX/standard/extended/последний ID и ошибки. TX должен быть0.
   При отсутствии трафика активные поиски не добавлять: проверить подключение,
   питание и состояние автомобиля в рамках отдельного аппаратного анализа.

## Ограниченный стандартный OBD-сеанс

1. Зажигание включено; запустить canfix19 или отдельно принятый кандидат. Не
   включать новые UDS-профили. Записать начальное состояние LISTEN и время.
2. Наблюдать переход к штатному поиску после независимого трафика. Запрос:
   standard11-bit, 7DF, DLC8, `02 01 00 00 00 00 00 00`. Ожидаемый положительный
   ответ поддерживаемых PID: 7E8..7EF, SF с `41 00` и четырьмя байтами bitmap.
   Новый код также принимает SF с DLC7; собственные запросы остаются DLC8.
3. Не нажимать многократно повторный поиск. Существующий лимит — до3 проб в раунде
   и до3 дополнительных раундов через5/15/30 секунд при свежем трафике. Дождаться
   штатного результата/QUIET; не держать бесконечный повтор.
4. Записать отдельно: confirmed TX, TX failed, ACK/bit/form/stuff/other,
   TEC/REC и peaks, BUS_OFF, RX dropped, arbitration/bus errors, ECU count/id,
   timeouts/rejected/malformed. Сравнивать изменения счётчиков, не только итог.
5. Если ECU найден: поддерживаемые PID, VIN-процедура и штатные RPM/speed/coolant/
   voltage. На стоянке скорость0; при безопасном запуске двигателя RPM должны
   отличаться от нуля и соответствовать reference. Нет данных — не значение0.
   Не проводить тесты разгона или движения ради этой проверки.
6. Если начался многофреймовый ответ, зафиксировать FF, подтверждённый FC на
   **физическом request ID**, CF SN и время завершения. FC `30 00 0A` разрешает
   непрерывный блок со STmin10 ms; ограничение буфера128 байт. Не отправлять FC
   на 7DF, случайный ответ или в listen-only.
7. При новом CAN fault/BUS_OFF, заметных предупреждениях автомобиля или проблемах
   питания прекратить опыт и отключить устройство. Повтор не подменяет диагностику.

## Получение доказательств

На стоянке локальная Web-страница → «Проверить состояние связи» читает снимок,
не отправляет CAN. «Скачать снимок проверки» сохраняет `/api/validation`.
Снимок содержит `connection_doctor` (новая ветка), исходные кадры/обмены и времена.
Кольца ограничены96 кадрами/16 обменами: поздний снимок может потерять начальные
кадры. Фиксировать снимок сразу при ошибке и отдельное фото счётчиков; переполнение
колец обозначено счётчиками. Не считать отсутствие кадра в усечённом кольце
доказательством его отсутствия на проводе.

Перед USB полностью отключить OBD. При USB-only прочитать
`MINIDASH_CAN_INCIDENT`, если он сохранён. Существующая запись сохраняется лишь
при QUIET после RX и TX failures, не при каждом таймауте приложения; максимум
одна попытка за boot. Если сохранена старая версия/старый incident, не приписывать
её этому сеансу. Успешный TX без ECU может не создать новую NVS-запись — для него
нужен Web-снимок/фото до отключения. Не стирать NVS ради получения отчёта.

VIN, raw frames и идентификаторы из live-снимков оставлять в локальных приватных
артефактах. В issue/PR публиковать только вручную проверенные обезличенные
счётчики, build ID и минимальный синтетический reproducer. F190 и Mode09/VIN могут
быть фрагментированы: простого удаления поля `vin` недостаточно.

## Интерпретация и следующий шаг

| Наблюдение | Допустимый вывод / следующий шаг |
|---|---|
| RX0, TX0 | Нет свидетельства активности: питание/зажигание/подключение/режим; gateway ещё не диагностирован. |
| RX есть, TX0 без отказов | Проверить LISTEN/QUIET, готовность адаптера и startup gate. RX не подтверждает способность передавать. |
| TX failed, confirmed TX0, ACK растёт | Передачи не подтверждены; проверить физическую связь/режим/тайминг отдельным анализом. Не делать вывод, что именно target ECU отсутствует. |
| BIT/form/stuff/other растут | Зафиксировать направления/TEC/REC и момент ошибки; это класс ошибки, не доказательство конкретного дефекта проводки. |
| confirmed TX>0, ECU0 | Некоторые CAN-кадры переданы с ACK. Проверять ответные ID/IDE, RX drops, timing, service и состояние ECU. Сам gateway не объявлять неисправным. |
| FF есть, завершения нет | Проверять FC confirmation, правильную физическую пару, SN, N_Cr, длину и RX loss. |
| `7F 22 78` | Принято ожидание, а не положительный ответ. В новой ветке P2*=5s, total10s, max3 pending; не пересылать запрос. |
| `7F 22 31` или иной NRC | ECU ответил отрицательно; проверить DID/идентичность/сессию. Не объявлять блок отсутствующим и не включать session hopping. |
| ECU обнаружен, метрика stale | Discovery ещё не означает текущую телеметрию; проверить capability, запрос/длину/decoder/TTL. |

## Когда можно перейти к gateway/DQ500/Haldex

Только после подтверждённого автомобильного TX и успешного стандартного обмена:
собрать точные gateway/ECU identities и физические пары разрешённым read-only
инструментом. Проверить лицензию/происхождение данных. Согласовать ограниченную
реализацию J533-пробы отдельным изменением; текущий helper работает лишь офлайн.
Не использовать `700+bit`, `+6A` или адреса OpenHaldex как готовый Tiguan scan.
Сопоставить 2A26/04A3 с реальным installation list, включая неизвестные/пропущенные
блоки. Промежуточные результаты остаются hypotheses, не polling permissions.

Критерий приёмки этого этапа: либо воспроизводимые корректные OBD ответы/свежие
метрики, либо сохранённое доказательство конкретного уровня отказа с build ID,
режимом, временными метками и ошибками. Точная электрическая причина может
потребовать отдельного измерения на шине; программный отчёт не заменяет его.
