# CYD 0.5.0: переключатель DEMO и подготовка CAN

Дополнительная платформа в `feature/hardware-cyd-esp32`; main не меняется.
Аппаратное испытание автомобиля и подключение SN65HVD230 пока не выполнены.
Это прошивка для следующего этапа сборки/проверки, не подтверждённая автомобильная установка.

## Поведение

Settings → последняя страница (7/7) → Demo mode / Демо-режим → Enable/Disable.
Touch выбирает строку, нижняя кнопка меняет режим, как у остальных настроек.
Консольная навигация вызывает тот же обработчик: `home`, `settings`, 24 раза
`down`, `select`. Смена не требует перезапуска или перепрошивки.

- ON: существующая симуляция, все синтетические сигналы помечены DEMO.
  TWAI остановлен/удалён. TX GPIO22 удерживается на recessive high.
- OFF: TWAI LISTEN_ONLY, 11-bit/500 kbit/s, TX22/RX27. Нет ACK, error frame
  или запросов. Синтетические значения удаляются, без источника показывается N/A.
- После отдельного подтверждения проводки доступен стандартный OBD-II:
  существующие acquisition/ISO-TP, capability discovery, выбор ECU, VIN,
  bounded polling и чтение DTC. Это диагностические запросы, не пассивное чтение.
  Запись/стирание DTC, управление исполнительными механизмами и UDS не добавлены.

Первое включение по умолчанию DEMO. Пользовательский выбор ON/OFF сохраняется
в отдельном NVS `md_cyd/demo` (u8 1/0), неизвестное значение безопасно даёт DEMO.
Разрешение OBD TX существует только до перезапуска/смены режима. Выключение DEMO
само по себе не разрешает передачу. Длительное удержание Diagnostics также
не снимает блокировку. Веб-предпросмотры, импорт и сброс оформления не меняют её.

Wi-Fi по-прежнему только вручную из Settings, без мастера/автостарта. AP/QR,
портал, автояркость, темы и калибровка переиспользуются.

## Реализация и совместимость

`cyd_mode.c/.h` — небольшая проверяемая политика состояний/разрешений и GPIO,
не новый диагностический движок. `vehicle_app.c` переиспользует текущий
`acquisition.c`, TWAI v2 legacy API ESP-IDF 5.5.5 и существующий display signal store.
CYD передаёт готовые `md_acq_snapshot` сразу в display store; второй полный
92-signal canonical store не выделяется. S3 сохраняет прежний analytics bridge.
Один vehicle task владеет всеми сменами драйвера и публикацией обоих источников;
двух одновременно публикующих симулятора/CAN нет. При смене сбрасываются
измерения, VIN, ECU identity, transport, trace и motion latch. Никакие
полученные ранее DEMO-значения не становятся реальными показаниями.

CYD не выделяет минутный derived analytics buffer; trace ограничен 16 кадрами,
exchange history — 4 обменами. S3 сохраняет прежние 96/16 и полную аналитику.
Для vehicle task добавлен compiler stack guard: кадр не более 2048 при стеке
4096 bytes на CYD (S3 — 6144/8192); измеренные кадры CYD: vehicle_task 176,
publish_cyd 752 bytes (это не полный call graph).

Schema 4 JSON, бинарный wire format и пользовательская компоновка не изменены.
Новый параметр физического источника вынесен из конфигурации дизайна. Старые
прошивки просто игнорируют отдельный NVS ключ. При откате 0.4.0 опять всегда
DEMO и нет CAN; перед откатом на 0.3.1 выбрать тему 0–13.
`/api/device.simulation` теперь показывает текущий источник;
`derived_analytics=false` корректно блокирует CYD analytics controls и при CAN.
Новая строка/седьмая страница Settings существует только у CYD; S3 остаётся 24/6.

Затронуты Kconfig, sdkconfig.cyd, vehicle/display controller, Settings/LVGL,
переводы, embedded Web feature gate, CMake/native/browser tests, updater/docs.
Новых зависимостей, сторонних ресурсов и лицензируемых игровых материалов нет.

## Сборка, загрузка и восстановление

Сборка штатными `tools/build_firmware.py minidash_cyd` / `esp32_s3` в ESP-IDF
5.5.5; для подготовленной среды этой рабочей папки использован `../Build.ps1`.
Ключи CYD: CAN_ENABLE=y, SIMULATION=y, TX=22, RX=27, STANDARD_OBD=y,
CAR_VALIDATION_MODE=y. Включённый STANDARD_OBD означает наличие движка;
runtime interlock блокирует NORMAL driver и каждую отправку до разрешения.

Оригинальный полный NerdMiner 4 MiB dump повторно проверяется перед загрузкой:
SHA-256 `904a38429a8b2b0863cab48ddafa06c15b3312ea2622389ae6962ed4e9412bc9`.
Текущая конфигурация и NVS 0x9000/0x6000 сохранены и сверены с устройством,
приватно в `outputs/can-mode-private/`, вне Git/публичного архива.
Updater проверяет исходный backup, SHA приложения и MAC этой платы; пишет только
app по 0x10000, затем отдельно verify-flash, перезапускает. Bootloader,
partition table, NVS и eFuse не переписываются. Готовый пакет содержит
`firmware/Update-CYD.ps1` и rollback app 0.4.0.

Из каталога пакета: `./firmware/Update-CYD.ps1 -Port COM4`.
Восстановление MiniDash 0.4.0: `python -m esptool --chip esp32 --port COM4
--baud 115200 write-flash 0x10000 firmware/minidash-cyd-rollback-0.4.0.bin`.
Полное восстановление NerdMiner: проверить SHA оригинального dump и записать
его по 0x0. Полный backup содержит приватные настройки и не входит в архив.
Не стирать flash перед обновлением приложения. Исправлена совместимость updater
с Windows PowerShell 5: пути по умолчанию вычисляются после блока param.
Первый вызов с прежними defaults остановился до записи; повторный с исправлением
проверил backup/MAC и выполнил app-only загрузку и отдельную digest verification.

## Подключение и первый сеанс

| CYD | SN65HVD230 breakout | Состояние |
|---|---|---|
| GPIO22 | CTX / D (chip pin 1) | Задано в прошивке, расположение контакта проверить прозвонкой |
| GPIO27 | CRX / R (chip pin 4) | Задано в прошивке, проверить маркировку и прозвонку |
| 3.3 V | VCC (chip pin 3) | Только 3.3 V, измерить на модуле |
| GND | GND (chip pin 2) | Общая сигнальная земля |
| OBD6 | CAN H (chip pin 7) | Проверить нужную шину конкретного автомобиля |
| OBD14 | CAN L (chip pin 6) | Перепутанные H/L не исправляются прошивкой |

GPIO35 — альтернативный RX только для отдельно пересобранного/проверенного
профиля; поставляемый образ использует GPIO27. TFT, touch, LDR, SD, RGB,
аудио, UART, boot straps и flash в CAN pin policy запрещены.
[Полная таблица, схема питания/защиты и CAN](minidash-cyd.md).
12 V OBD16 → предохранитель → защита/TVS → автомобильный DC/DC5V → CYD5V;
CYD3.3V → CAN VCC. Нельзя подавать 12 V на CYD или 5 V на SN65HVD230,
соединять одновременно USB5V ПК и выход DC/DC без развязки.

До передачи необходимы проверенные схема и распиновка реального модуля,
VCC/GND/RS, отсутствие лишнего 120Ω терминатора на уже оконцованной сети,
защита/питание и подтверждение 11-bit500k OBD. Наличие терминатора, напряжения
и проводка программно не измерены. Не считать этот отчёт их подтверждением.
Сначала изолированный стенд и приём CAN; на стоящем автомобиле DEMO OFF,
в Diagnostics должен расти RX при TX=0. Без профиля пассивные кадры ещё не
декодируются в RPM/температуры: N/A до разрешённых OBD-запросов ожидаем.

Только после фактического подтверждения проверенной схемы используется
maintenance UART команда `can-arm CONFIRM_WIRING_22_27_3V3` (115200).
Дополнительно код требует применённый MONITOR и исправный driver.
RX полезно проверить до запросов, но готовый стандартный OBD-сеанс может
начинаться с запроса: отсутствие фоновых кадров не заменяет подтверждение
проводки и не образует искусственную блокировку запуска.
Команда не вызывается тестами/прошивальщиком автоматически. `can-disarm`
немедленно блокирует новые запросы и возвращает listen-only; перезапуск тоже
снимает разрешение. В нынешней аппаратной приёмке разрешение не выдавалось.
Для постоянного ежедневного запуска нужен последующий проверенный installation
preset после автомобильного испытания; нынешний arm намеренно не сохраняется.

Стандартные поддержанные ECU PID могут дать RPM, скорость, coolant, load,
MAP/ambient pressure, ECU voltage, engine oil, IAT, ambient air, STFT/LTFT.
DSG oil, gear, AWD, VAG-specific boost и прочие непроверенные DID остаются N/A.
Нет универсального VAG-профиля, CAN FD или 29-bit OBD в этом preset.

## Обнаруженная и исправленная нехватка SRAM

Первый аппаратный прогон версии с CAN дал 61 HTTP PASS / 8 FAIL: четыре
страницы не проходили parse/preview, минимум свободного heap упал до 16 bytes.
Та же фактическая конфигурация проходит native validator; потерю настроек
исключили сравнением экспорта, selftest восстановил исходную конфигурацию.
Причина — лишний полный signal store плюс запас стека и пересечение временных
JSON буферов локального HTTP клиента/сервера на двух ядрах.

Промежуточное уменьшение store/стека пропустило первый 4-page preview, но
следующие запросы ещё упирались в heap (62 PASS / 7 FAIL); исходная конфигурация
снова была восстановлена и сверена. В финальном образе CYD убрана эта копия store; vehicle stack уменьшен после
измерения GCC frame до 4096 и доступен `stack_free` в source status. Перед
построением parse tree HTTP сервер уступает один RTOS tick, позволяя локальному
maintenance client освободить отправленный JSON и TCP буферы. Пределы страниц,
схема, строгая валидация, публичный API и набор проверок не урезаны. Это не
повтор отклонённой записи. Публикация копирует только raw snapshots, а не весь S3 status на стек.
CYD AP также использует runtime wifi_init_config: static RX2, dynamic RX4/TX4,
BA window2, RX management2, management short6 (допустимый SDK minimum).
Исходные Kconfig defaults остаются прежними; эти overrides только для CYD AP.
Это компромисс throughput/буферов для ручного конфигуратора. S3 не использует
эти overrides, delay или уменьшение стека.

После экономии SRAM отдельный 69/69 прогон прошёл, а полный прогон после
переключений дал 68/69 (одна смена темы). Найден обратный порядок mutex:
UI синхронизировала config → LVGL, HTTP использовал LVGL → config. На CYD
порядок UI приведён к LVGL → config; LVGL mutex в esp_lvgl_port recursive,
существующие вложенные вызовы сохранены. S3 порядок не меняется. Источник
посылает vehicle context только при изменении, вместо повторов UNKNOWN10Hz.
Внутренний HTTP клиент теперь журналирует status/error неуспешных ответов
без содержимого конфигурации, чтобы отделять ожидаемые 400/403/409 от сбоев.

Дополнительный повтор selftest сразу после первого выявил отдельный SRAM
peak: debug client каждый раз создавал ещё 8 KiB task с deferred deletion.
На CYD `web-test` теперь синхронно работает на уже выделенном 8 KiB main/UART
стеке; дополнительные задачи/стеки не создаются. UI, CAN и AP — независимые
задачи и продолжают работу. Консоль ждёт конца служебного теста; это не меняет
обычные HTTP/API запросы телефона. S3 оставляет асинхронный selftest.

## Проверки и оставшийся этап

Итоговые измерения USB и хеш приложения приведены в `minidash-cyd-can-mode-verification-2026-10-20.json`.
Native CTest проверяет исходный S3 и отдельно CYD core/acquisition с меньшими
буферами; policy test перебирает все комбинации разрешения, некорректный NVS
и GPIO exclusions. Chromium проверяет реальный embedded HTML с fixture HTTP
и нативным C validator, включая CYD CAN source с выключенной аналитикой.
Эти проверки не являются CAN electrical/vehicle или физической touch проверкой.

Оставшиеся шаги: (1) собрать/измерить защищённое питание и трансивер по таблице;
(2) изолированно проверить TWAI RX/терминацию; (3) подтвердить схему, разрешить
ограниченный OBD на стоящем автомобиле, сопоставить capability/PID/единицы с
эталоном и сохранить validation trace; (4) только по доказательствам подготовить
VAG profile и постоянный installation preset. Риск без этих этапов — неверная
распиновка, питание/терминация либо неподдерживаемый автомобильный протокол.

Источники: локальные `driver/twai/twai.c`, `driver/twai/include/driver/twai.h`
ESP-IDF5.5.5 (реально используемый legacy v2 API),
[Espressif TWAI](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/peripherals/twai.html),
[TI SN65HVD230](https://www.ti.com/product/SN65HVD230).
Внешняя документация сверена 20 октября; конкретную плату/модуль она не аттестует.

## Итог аппаратной приёмки

На COM4 записан финальный app 1969184 bytes, SHA-256
`d4a238223dae6e5d0c1fc7da7da19bb329c99b85bac9102dd6814c5886fadc29`; отдельный verify-flash: digest matched.
15/15 native, 43/43 Chromium fixture checks, 27/27 реальных UI core/LVGL и 69/69
HTTP на ESP32 в каждом из двух последовательных прогонов прошли. 31 этапов USB-приёмки заняли 239.5 s.
Минимальный heap финального прогона после reset: 13588 bytes;
минимальный запас vehicle stack: 1980 bytes.
Сравнимый home/monitor heap до/после пяти полных циклов: 139228 / 138720 bytes.
DEMO OFF пережил реальный RTS reset; calibrated=1 и AUTO сохранены, selftest
сравнил calibration blob до/после. Полный common (кроме last_screen) и platform
совпали с предшествующим экспортом. В конце оставлены Home, DEMO OFF,
Wi-Fi OFF, CAN LISTEN_ONLY, TX=0. Активная передача не разрешалась.
Переходы OFF/ON и 4-page preview повторно прошли после исправления SRAM.
Физические касания/изображение LCD не наблюдались агентом; внешнего телефона,
подключённого трансивера, электрической CAN проверки и автомобиля в приёмке нет.
S3 собран, физически не прошивался. Это короткий стендовый прогон, не длительный
термический/автомобильный soak.
