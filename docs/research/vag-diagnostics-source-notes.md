## CPS3 source audit: useful comparison, not transport reference implementation

Pinned source: [CAN_Driver.cpp](https://github.com/lilsteelan/cps3-dashboard/blob/3c8780621ff568de55a3d042da56e14046e883ff/CAN_Driver.cpp), [audi_uds.h](https://github.com/lilsteelan/cps3-dashboard/blob/3c8780621ff568de55a3d042da56e14046e883ff/audi_uds.h), [skoda_uds.h](https://github.com/lilsteelan/cps3-dashboard/blob/3c8780621ff568de55a3d042da56e14046e883ff/skoda_uds.h).

- Explicit engine 0x7E0/0x7E8 and gearbox 0x7E1/0x7E9; Audi brakes 0x713/0x77D; Skoda steering 0x712/0x77C and gateway 0x710/0x77A. These are configured constants, not discovered installation-list mapping.
- Sends Mode01 functionally to 0x7DF; static Mode22 uses physical IDs, 8-byte DLC, 0x55 padding. send helpers return twai_transmit enqueue success, not controller-confirmed TX. MiniDash canfix19 has a stronger contract already.
- Normal UDS parser accepts SF 0x62 and dispatches on DID alone, without matching response CAN ID or outstanding request. Header comments say DIDs are globally unique, but 0x028D is used for both engine and transmission with different scaling in audi_uds.h. No incoming payload-length argument reaches decoder; source has no robust transaction ownership. Do not replicate.
- Normal acquisition path supports single-frame UDS; the optional disabled DID sweep has a separate small multi-frame/FC path, not a general reusable UDS client. Scanner supports broad DID ranges when enabled; explicitly out of MiniDash scope.
- Poll loop transmits one request every 50 ms and prioritizes Mode07 every 2 s. It does not wait for completion or an active-request flag; “one outstanding” comments and commit prose overstate implementation. Slow responses can overlap.
- CAN status is polled around 1 s; BUS_OFF triggers recovery and STOPPED restart. No exact ACK/bit error evidence in this path.
- Page-aware fast/slow tiers and stale-data invalidation are useful product ideas, already implemented more systematically in MiniDash demand/TTL/source arbitration.
- Same-platform DID divergence is concrete: Audi oil temp 0x202F vs Skoda 0x11BD; transmission temp 0x2104 vs Skoda 0x38B2; engine BE and gearbox LE. These refute universal MQB DID/scaling assumptions.
- [Commit 8df7e4f](https://github.com/lilsteelan/cps3-dashboard/commit/8df7e4f356c1adf68be66715c8460d60b5ab48dc) explains page focus; sampled API issue list was empty. Absence of issues is not verification. No automated transport test harness was found in inspected file inventory.

## opendbc source audit

Pinned paths: [Volkswagen values.py](https://github.com/commaai/opendbc/blob/c3955753ae7258412814e2cdca3ee8af979e4679/opendbc/car/volkswagen/values.py), [fingerprints.py](https://github.com/commaai/opendbc/blob/c3955753ae7258412814e2cdca3ee8af979e4679/opendbc/car/volkswagen/fingerprints.py), [isotp_parallel_query.py](https://github.com/commaai/opendbc/blob/c3955753ae7258412814e2cdca3ee8af979e4679/opendbc/car/isotp_parallel_query.py), [uds.py](https://github.com/commaai/opendbc/blob/c3955753ae7258412814e2cdca3ee8af979e4679/opendbc/car/uds.py).

- Volkswagen identification query concatenates F187 (manufacturer spare part number), F189 (software version), F182 (application data identification) into one service-0x22 request. F187 comments explicitly discuss tampered part numbers, useful for avoiding overconfident identification.
- Response offset +0x6A applies to configured SRS/EPS/radar/camera; default +8 to engine/transmission. This is strong code evidence that a universal “response=request+8” rule fails outside legislated powertrain addresses. Logical VAG module numbers still are not CAN IDs.
- Firmware query configs explicitly vary CAN bus and OBD multiplexing. A CAN tuple must include connection point/bus, IDE/address mode and TX/RX, not just a number.
- This is whitelisted ECU firmware identification, not J533 installation-list discovery. Tiguan Mk2 fingerprint entry contains many engine and gearbox variants; broad platform membership must not unlock DIDs.
- Generic IsoTpMessage supports segmentation, CF sequence, flow control, selectable block behavior and millisecond/microsecond STmin. Parallel query uses 10 ms receive separation, per-address timeout, progress extension on CF, NRC78 extension (default 10 s) and overall 60 s cap. MiniDash should preserve tighter explicit limits rather than import a concurrent discovery model.
- Important limitation: parallel query at this snapshot treats unexpected payload byte 2 == 0x78 as pending without strict 7F/original-service validation. Mature ecosystem does not imply every edge case is correct.
- [Open PR #3892](https://github.com/commaai/opendbc/pull/3892) was inspected: proposes malformed ISO-TP length/state validation, same-bus functional replies, stale-frame drain, ignoring empty frames and late responses. Author reports 18 transport regressions, 15 firmware tests, 255 interface tests, 49 CAN tests, with no hardware validation. These are upstream claimed results, not run here; PR is open and not part of pinned HEAD. It fixes [issue #1684](https://github.com/commaai/opendbc/issues/1684), worth following for interoperability lessons.
- Reuse existing MiniDash MIT-pinned MQB subset/provenance path. Do not import full DBC into active firmware or infer telemetry availability from parser definitions. No opendbc actuation/carcontroller behavior belongs in MiniDash.

## Additional Haldex investigation

Pinned [OpenHaldex diagnostic source](https://github.com/meatro/OpenHaldex-S3/blob/efc6f239d755ec24213406ae34f03f681df10dfa/src/functions/diag/uds.cpp):

- Candidate routes are 0x70F/0x779 standard, 0x71D/0x787 standard, and 0x1C40000F/0x1C42000F extended. F19E is used as exact echoed DID to choose a route; positive response must be 62 F1 9E. Cached selected route is tried first; timeout clears selection.
- RX observes only active response ID and IDE, uses bounded queues plus a diagnostic mutex. FC is CTS, BS=0, STmin=0; receive supports SF/FF/CF and sequence checks, bounded total request time, exact NRC78 SID matching. This is useful architectural evidence for serial transaction ownership and cached-route revalidation.
- Routes are candidates for the source's direct Haldex bus; do NOT convert all three into a Tiguan OBD scan. F19E support alone identifies a responding route, not exact compatible ASAM data definition.
- The same file exposes 0x14 DTC clear and older KWP session logic. Those operations are excluded from MiniDash. No need for SecurityAccess, downloads, basic settings, control-frame mutation or bus bridging.
- [Issue #12](https://github.com/meatro/OpenHaldex-S3/issues/12) reports ESC faults when heavily using Web UI. It is a user report, unresolved, not evidence to diagnose MiniDash. It does reinforce independent bounded CAN servicing and snapshot-based UI export.
- Recent inspected commits include docs clarification efc6f239, standalone configuration PR #6, and build workflow PR #5. Latest source vs installer/release names must be distinguished; root MIT does not imply every current branded installer/artifact has that license.

## Non-GitHub sources and what they establish

All accessed 2026-10-22; no code/data copied.

1. [Ross-Tech Gateway Installation List](https://www.ross-tech.com/vcds/tour/installation-list.php): newer gateway inventory can be accessed through logical module 19; UDS direct coding is a bitfield; UI also contains writes. This establishes installation-list concept but publishes neither a universal DID nor a CAN-ID conversion. MiniDash must implement only the evidenced read and never “register” modules.
2. [Ross-Tech Advanced Measuring Values](https://www.ross-tech.com/vcds/tour/adv-meas-blocks.php): UDS/ODX/ASAM values use factory identifiers such as IDEnnnnn; sampling depends on controller and number of values; grouped requests may improve rate but have compatibility caveats. An IDE name is not itself a wire DID. Rate optimization follows correct single-transaction operation, not before it.
3. [Ross-Tech DQ500 page](https://wiki.ross-tech.com/wiki/index.php/7-Speed_Direct_Shift_Gearbox_%28DSG/0BH/0BT%29): identifies DQ500/0BH/0BT and UDS advanced measuring values; related variants are mentioned. It is primarily a basic-settings service procedure, not a public DID/scale map. No basic-settings operation was executed or recommended for MiniDash. No exact DQ500 telemetry map was verified from it.
4. [Auto Fault Finder Gen5 Haldex guide](https://www.haldexrepairs.co.uk/generation-5-haldex-fault-finding-repair-guide/): independent specialist says Gen5 lacks a pressure sensor and diagnostic pressure values are calculated; identifies logical AWD address 22. Treat as secondary mechanical guidance: label estimated quantities as estimates, do not call them measured pressure or diagnose pump health from a single derived value. Repair/adaptation instructions on page are outside scope.
5. [Official OpenHaldex documentation](https://openhaldex.com/docs/) and [compatibility](https://openhaldex.com/compatibility/): public product claims Gen5 MQB 0CQ and PQ 0AY UDS telemetry, with model lists. These are not independent validation or packet layout; source above is a different project's concrete implementation, not proof of identical product behavior.
6. [MQB Gateway routing discussion](https://www.reddit.com/r/CarHacking/comments/1qx7y0r/mqb_platform_gateway_routing_for_uds_to_modules/): search result describes ESP32 access to engine/TCU but difficulty reaching other modules. This is a research lead only; not used as a protocol authority or root-cause proof.

## MiniDash architecture mapping: extend existing components

| Proposed capability | Existing boundary | Recommended evolution / acceptance gate |
|---|---|---|
| CAN Connection Doctor | vehicle_app.c adapter/status plus canfix19 alerts, controller-confirmed sends, trace and persistent validation report | Classify mode/bus-activity/TX result/error-capture/ISO-TP/UDS stages in existing snapshot. Report unknown distinctly; ACK proves some peer, not target ECU. No second task reading TWAI alerts. |
| Vehicle Discovery Manager | acquisition.c OBD discovery, supported PID maps, VIN/identity states; host discovery.py | Add bounded offline-tested gateway parser/registry, then explicit evidenced physical endpoint probing. Keep request owner in acquisition. Inventory-present is not ECU-reachable; timeout is not absent. |
| ECU Registry | Native responders[8] plus single profile; host EcuIdentity/IdentityContext, knowledge | Bounded per-ECU records with route/IDE, evidence and response status. Reconnect revalidation mandatory; cached capability cannot grant TX. Avoid persistent VIN in public diagnostic exports. |
| Read-only UDS Client | diagnostic_transport.c ISO-TP plus acquisition.c service validation; host uds.py | Harden existing transport and pending handling, not parallel client. Default session only; request allowlist; no auto session/TesterPresent unless explicitly evidenced and enabled later. |
| DID Capability Registry | profile bindings, host registry.py/knowledge.py/provider provenance | Separate unsupported NRC31/11 from timeout; binding includes exact ECU fingerprint, byte order, scale, bytes, unit, evidence. Native big-endian scalar-only bindings cannot directly ingest little-endian gearbox examples. |
| Adaptive polling | acquisition.c visible/background demands, per-job due/failure arrays, single active exchange, source TTL | Preserve bounded one-outstanding and rate/backoff gates; discoveries must not starve critical signals or send unbounded retries. UI should consume snapshots only. |
| Diagnostic UI/export | vehicle status, trace ring96/exchange ring16, GET /api/validation, physical diagnostics page | Add stage reason and registry summary to current data model; avoid second frontend or synchronous bus calls from HTTP. Existing analytics should stay independent of protocol specifics. |
| Offline replay | Host replay.py/CanTraceReader + native shared acquisition/transport replay tests | Use synthetic malformed/incomplete/negative/multi-ECU traces through real production functions. Offline is never promotion to real-car validation. No new replay engine. |

Current native constraints matter: profile is one exact VIN/ECU/endpoint, request/response IDs are uint16_t, manufacturer bindings are big-endian scalars, and default profile is NULL. Host knowledge is broader, but adding definitions there does not activate native polling. A full multi-ECU 29-bit system is more than changing an ID constant. For this task, strongest return is P0/P1 hardening plus an experimental no-transmit inventory parser/registry and a concrete car evidence plan. Exact DQ500/Haldex telemetry remains deferred until fresh ECU identity + captured request/response + scale evidence are available.
