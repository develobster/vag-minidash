# Аппаратная база и стенд — 0.6

Базовое решение пересмотрено в сторону стоимости и проверяемости. ESP32-P4 и узкий
MIPI-DSI AMOLED не входят в первую версию: это аппаратный ориентир отдельного премиального
устройства, а не обязательная часть VAG MiniDash.

## Принятая архитектура

| Версия | Состав | Назначение |
|---|---|---|
| V1 | Windows/Linux-приложение + имеющийся VNCI 6154A/совместимый диагностический транспорт | Сначала проверить блоки, DID, DTC и одну безопасную функцию на реальном автомобиле |
| V2 | ESP32-S3 + внешний CAN-трансивер + небольшой SPI/I²C OLED + 3 кнопки | Автономный дисплей в духе Clever, без MIPI и Linux |
| Premium | Более мощный MCU + цветной MIPI-дисплей | Только если понадобится сложная графика, карты или touch-интерфейс |

Для V2 ориентир по корпусу — устройство Clever: 99×37×13 мм, OLED и до восьми параметров
на одном экране. По фото это узкий монохромный графический OLED; разрешение и контроллер
нужно определить по конкретному модулю, а не угадывать по внешнему виду.

## Что не покупаем на первом этапе

- ESP32-P4, MIPI-DSI AMOLED и отдельную wide-PCB;
- собственную плату до проверки транспорта на автомобиле;
- ELM327 для задач, где нужны CAN/ISO-TP/UDS и запись.

## Исторический аппаратный ориентир

Репозиторий DPF Load Monitor Wide использует ESP32-P4, AMOLED 3.19 дюйма 262×928,
MIPI-DSI и шестислойную PCB. Он остаётся справочным примером компоновки и логирования,
но не определяет BOM базовой версии MiniDash. Источник: https://github.com/v-cu/dpf-load-monitor-wide

## Стенд и реальные данные

| Этап | Комплект | Условие выбора |
|---|---|---|
| Стенд | VNCI 6154A или USB-CAN с документированным API | Сначала read-only и журнал обмена |
| Стенд | Кабель, безопасная CAN-сеть | Проверенные распиновка и терминаторы |
| Устройство V2 | ESP32-S3, CAN-трансивер, OLED, кнопки | После подтверждения нужных данных на V1 |
| Устройство V2 | Питание от автомобиля и корпус | После проверки переходных процессов, сна и нагрева |

Конкретный товар USB-CAN, цены и наличие в РБ не подтверждены. ELM327 не считать
заменой SocketCAN-адаптера. VNCI 6154A не поддержан: для него нужен отдельный backend.
Плату заказывать после ревью схемы/BOM/лицензии и проверки доступности нужного экрана.

## Данные для реального кодирования

Через имеющийся ODIS сохранить идентификацию двигателя, коробки и целевого блока:
номер детали, HW/SW, версию ПО, ASAM/dataset (если видны), текущую кодировку и карту
нужных адаптаций. VIN при передаче можно скрыть. Базовые установки и прошивка для этого не нужны.

## CAN-регистратор

Linux, стандартный Python, без pip. Classical CAN 11/29-bit, RTR/error frames, JSONL,
лимит времени и числа кадров. Данные пока не переводятся в показатели двигателя и
не подмешиваются в симулятор. Время — получение приложением, не аппаратный timestamp;
потери сокета не считаются, полнота лога под нагрузкой не гарантирована.

На уже настроенном интерфейсе:

```sh
python can_capture.py capture --channel can0 --output capture.jsonl --seconds 60
python can_capture.py inspect capture.jsonl
```

Программа не вызывает send и не делает UDS-запросов. Аппаратный listen-only автоматически
не включается: обычный CAN-контроллер может передавать ACK. Режим и скорость контроллера
проверять отдельно; распиновку сети не угадывать. Шлюз автомобиля может не выдавать нужный
трафик пассивному наблюдателю — позднее потребуется активная диагностика.

Виртуальный Linux-стенд без автомобиля (настройка требует прав администратора):

```sh
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up
python can_capture.py capture --channel vcan0 --output virtual.jsonl --seconds 30
```

Из другого терминала с установленным can-utils, только в виртуальную сеть:

```sh
cansend vcan0 123#10203040
```

Завершение по лимиту/времени/Ctrl+C; существующие файлы не перезаписываются.
Тесты формата и receive-path на mock-сокете пройдены. Физический CAN и vcan в этой среде
не проверены. ESP-IDF/LVGL и реальная запись кодировок остаются следующими этапами.

## ESP32-S3 bring-up

Для существующего ESP-IDF каркаса добавлен диагностический self-test платы ESP32-S3.
Команды Windows/COM4–COM5, ограничения безопасных GPIO-проверок, PASS/FAIL сбор evidence и
описание записываемых образов: [docs/hardware/esp32s3-bringup.md](docs/hardware/esp32s3-bringup.md).
Тест не включает CAN и не очищает Flash целиком.

Источники API:
https://docs.kernel.org/networking/can.html
https://python-can.readthedocs.io/en/stable/interfaces/socketcan.html
